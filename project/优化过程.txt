思考3过程的，（主要在于优化sb的bank冲突问题）
方法论1：采用padding，无法直接解决128列长的问题，现在想想可能分组padding可能能解决问题。
方法论2，采用swizzle，swizzle感觉没有padding好用，在不使用tensor core的基础上。并且额外
带来索引计算损失，但无论怎么样都不如以数学改索引来的好用。
方法论3，采用合并读取加线程束洗牌，效果不佳，线程束洗牌只能对单一变量进行操作，无法对float4
进行操作，多导致额外多出四次运算。

这里能优化的点，采用多缓冲区，并且加上sa转置+sapadding分组padding写法。这里附上专门的padding写法
感觉能优化0.1ms+，这里核心的多缓冲区去隐藏sa转置的读取，然后计算我觉得已经做到最优了，
主要转置会多增加访存的压力，但是计算做到最优，利用多缓冲区弥补访存的压力。
    #pragma unroll
    for (int i = 0; i < 4; ++i) {
        int load_idx = tid + i * 256; // 0 ~ 1023 
        int r = load_idx / 8 %32;        // A 矩阵全局行 (0 ~ 127)
        int g = load_idx / 8 / 32;    // A 矩阵全局行组 (0 ~ 3)
        int c_f4 = load_idx % 8;     // A 矩阵全局列 float4 索引 (0 ~ 7)
        int global_row = g * 32 + r;          
        float4 val = *reinterpret_cast<const float4*>(A + global_row * K + c_f4 * 4);
        //sa是2*128*36
        smem.compute.s_a[write_stage][c_f4 * 4 + 0+g*32][r] = val.x;
        smem.compute.s_a[write_stage][c_f4 * 4 + 1+g*32][r] = val.y;
        smem.compute.s_a[write_stage][c_f4 * 4 + 2+g*32][r] = val.z;
        smem.compute.s_a[write_stage][c_f4 * 4 + 3+g*32][r] = val.w;
    }

对写回显存的操作，之前索引没改前是8路冲突还是4路冲突，现在索引改了则会合并写，效率增高.之前
想过没改前的8/4路冲突，采用双缓存区，由共享内存寄存，再合并写，性能会得到一定的提升。



针对tensor core的描述。
采用四缓冲区和双缓冲区和一SM两个block，
四缓冲主要解决的是显存到共享内存的压力，双缓冲区和一SM两个block主要解决的是指令延迟，这里其实没有测试过，但感觉依然为访存压力更大些。

共享内存的A和B分别为128*64，64*64.mma运算采用16*8*16的运算，综合而言tensor core是采用内积，而非tensor core内部却采用外积思维，思路不一样。

假定A和B都为行主序（但现实中采取B为列主序的方式，这样更好些）。
这里在显存传递到共享内存采用128b的swizzle，由tma自动生成的，这里注意显存的AB为行主序，共享内存依然为行主序。
这里对于共享内存到寄存器采用ldmatrix.sync方式，即ptx方式，可以更好掌控寄存器，其中A采用非转置，B采用转置。
即A在逻辑寄存器中是行主序，B在逻辑寄存器中是列主序。
关于每个寄存器中具体存的哪个（笔记上会有记载），这里索引会很麻烦，但注意的是，由于tensor core需要特殊的写法，因此在索引上必须采用官方的，包括swizzle。因此能变动空间不大。
额外注意的是，tensor core的运算并不是一个线程的a和b，必须以全局的warp的所有a和b同时观看。

写回复用了共享内存，并且采用padding的方式解决bank 冲突问题，这里能复用共享内存足够大。
